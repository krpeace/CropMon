# 0042. 대표 밖 87곳 계산 조건(scenarios) 시드 및 '검증 전' 안내 정책

- **날짜:** 2026-11-10
- **상태:** 채택
- **연관:** 이슈 #103, croplib-dp #28 (C6, S5), 결정 0005, 결정 0012, 결정 0038, 결정 0039

## 왜

1. `croplib-dp` #28 2단계-나 S5에서 기상청 단기예보 기반 3일 물 전망 수집 대상을 대표 10곳에서 현행 운영 97곳 전체로 확대합니다.
2. 물 전망 표(`water_outlook`, `water_outlook_summary`)는 `scenario_id` 외래키(`references public.scenarios(scenario_id)`) 제약조건이 걸려 있으므로, 수집기가 가동되기 전에 DB에 해당 조건이 반드시 등록되어 있어야 합니다.
3. 대표 밖 87곳에 대해 비회원 기본 화면에 필요한 계산 조건을 사전 시드하고, 춘천 외 지점의 물 전망에 대한 '검증 전' 표시 정책과 대량 시나리오 조회 시의 안정성을 정립합니다.

## 결정

1. **시즌 연도: 2026년과 2027년 동시 등록 (총 348행)**
   - 2026년 작기(사과 10/27, 배추 9/28)는 종료되었고 2026년 물 전망(`water_outlook`)은 소급하지 않습니다. 2026년분이 필요한 이유는 `croplib-dp`가 2026 작기 돌아보기(`water_balance_daily`)를 소급 계산하는 대상이기 때문입니다(`croplib-dp` #87 계획 §7). 또한 S5 전망 적재가 시드된 조건을 참조합니다.
   - 50일 뒤인 2027-01-01에 조회가 즉시 2027년으로 전환되므로, 연초의 조건 누락 장애를 예방하기 위해 2027년 174행도 함께 등록합니다.
   - 단일 마이그레이션 파일(`20261110000000_seed_scenarios_non_rep.sql`)에 `on conflict (scenario_id) do update set` 멱등성을 보장하여 작성합니다.

2. **대표 밖 87곳 기본 2조건 선정 (사과 k3, 여름배추 k1)**
   - 폐지·휴지 8곳(관악산, 대구(기), 무안, 삼척, 성산, 성산포, 주암, 진도(첨찰산))을 정확히 배제하고, 현행 운영 87곳만 등록합니다.
   - 토성은 기본 양토(`loam`, FC 0.25, WP 0.12), 초기 고갈량 `dr0_mm = 0`을 적용합니다.
   - 사과(`apple-main`, `apple-k3`): TAW 130 mm, RAW 65 mm, 작기 04-01 ~ 10-27, `is_default = true`
   - 여름배추(`kimchi_cabbage-summer`, `kimchi_cabbage-k1`): TAW 65 mm, RAW 29.25 mm, 작기 07-01 ~ 09-28, `is_default = true`

3. **대표 밖 비기본 재배 방식 선택 시 친절한 안내 문구 분기**
   - 대표 밖 87곳은 기본 2조건만 계산하므로, 사용자가 사과의 다른 재배 방식(청경 재배 등 `is_default = false`)을 탭했을 때 기존의 획일적인 문구 대신 명확한 안내를 제공합니다:
     > _"대표 지점 밖은 기본 재배 방식만 계산해요. 다른 재배 방식은 가까운 대표 지점을 골라 보세요"_
   - 기본 재배 방식인데 조건이 없을 때는 기존 문구(_"이 지점은 아직 물 계산을 하지 않아요. 가까운 대표 지점을 골라 보세요"_)를 유지합니다.

4. **"검증 전" 표시 정책 유지 및 확대**
   - 결정 0012에 따라 예보 오차표 보정은 춘천(101)만 적용되어 있습니다 (`FORECAST_CALIBRATED = [101]`).
   - 대표 밖 87곳 역시 춘천의 오차 범위를 빌려 쓰므로, 단기예보 관수 필요일이 계산되었을 때 하단에 안내 문구(_"이 지점의 예보 범위(빠르면·늦으면)는 춘천 값을 빌려 써서 아직 검증 전이에요."_)를 그대로 자동 노출합니다 (`OutlookCard.tsx` 컴포넌트 수정 없음).

5. **`status-source.ts` scenario_id 100개 단위 청크 분할 읽기**
   - 기본 시나리오 수가 20개에서 194개로 증가함에 따라, Supabase API 호출 시 URL 쿼리 파라미터 길이가 ~6.9 KB에 달해 게이트웨이 버퍼(8 KB)에 근접하는 문제가 발생할 수 있습니다.
   - `scenario_id` 목록을 사용하는 3개 메서드(`summaries`, `recentBalance`, `outlookDays`)에 `chunkedByScenarios` 공통 도우미를 적용해 100개 단위로 병렬 분할 조회(`Promise.all`) 후 결과를 합칩니다.
   - 요청 URL 길이가 ~3.5 KB로 반감되어 안전하며, 한 묶음이라도 실패하면 전체가 즉시 reject되어 부분 집계 왜곡을 방지합니다.

6. **Egress 부하 분석**
   - 첫 화면 판정 표는 결정 0038에 의해 30분 수명(`cacheLife: 1800`)으로 하루 최대 48회만 실행됩니다.
   - 194조건 × 7일(1,358줄)의 1회 조회 순 증가분은 원시 JSON 기준 약 120 KB, PostgREST 압축 전송 시 약 20~25 KB입니다.
   - 하루 Egress 증가는 인스턴스당 약 1.2 MB/일(월 80~110 MB) 수준으로 Supabase 무료 한도(5 GB)의 2% 미만으로 극히 안전합니다.
   - 위 수치는 추정치이며, 11/10 17시 및 11/11 02시 회차 실행 뒤 Supabase 대시보드 텔레메트리 실측으로 최종 확인합니다.

## 실행 및 배포 원칙

- 실제 진행 순서: `croplib-dp` S5-a(#97, 2026-11-11 병합) → CropMon `#125` 병합(2026-11-13, `518f612`) → 사용자가 Supabase SQL Editor에서 시드 실행(2026-11-13 00시경) → 확인 조회 3개(`croplib-dp` ①-2창이 읽기 전용으로 실행: 연도별 기본 194개, 87곳×2, 폐지·휴지 0개) → `croplib-dp` 작은 dry-run → `NONREP_SCENARIOS` 켜기.
- (이력) 당초 계획에서는 시드 SQL 실행과 확인 조회 검증 뒤 PR `#125`를 병합하는 순서였으나, `croplib-dp` S5-a(#97) 병합 뒤 `#125`를 먼저 병합하고 시드를 실행하는 순서로 정정되었습니다.
