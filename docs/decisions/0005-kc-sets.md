# 0005. 데이터 계약 v1.1: 재배 방식별 Kc

- 날짜: 2026-10-24
- 상태: 확정

## 배경

v1의 작물 사전(`crops`)은 작물마다 Kc 칸이 한 벌뿐이어서 사과는 FAO-56 Table 12 시나리오 1(청경 재배, 서리 지역)만 들어 있었다. 현장 PC(cropwater)는 한국 사과원에 맞는 시나리오 3(초생 재배, 서리 지역)을 쓴다. 이대로면 서버와 현장 PC의 물 부족량이 다르게 나온다(croplib-dp 결정 0002에서 발견).

## 결정

- **재배 방식별 Kc 표 `crop_kc_sets`를 더한다.** 사과 4가지(Table 12), 배추 1가지. cropwater의 "시나리오 1~4"와 번호가 같다. 이름은 `scenarios`(계산 조건)와 헷갈리지 않게 "재배 방식"으로 부른다.
- **사과 기본은 3번(초생 재배, 서리 지역, 0.50 / 1.20 / 0.95).** 한국 사과원은 대개 과원 바닥에 풀을 키우고 겨울 서리가 내린다 (2026-10-24 사용자 결정).
- **11/06 비회원 화면부터 사용자가 재배 방식을 고른다** (2026-10-24 사용자 결정). 화면은 계산하지 않으므로, 공개 조건을 재배 방식마다 미리 계산해 둔다. 공개 조건은 20개에서 50개(지점 10 × (사과 4 + 배추 1))가 된다. 사과 물수지 계산량과 DB 행이 4배가 되지만, 한 해 지점당 약 300일 × 50조건 = 1만 5천 줄로 DB 용량에는 문제가 없다.
- **계산 조건 이름에 재배 방식 번호를 넣는다:** `101-apple-main-k3-loam-2026`. 지점·작물·연도마다 기본 조건(`is_default`)은 하나이고 기본 재배 방식이다.
- **`crops`의 Kc 칸은 지우지 않고 사본으로 남긴다.** 지우면 v1 사전 자료 파일을 다시 실행할 때 오류가 난다. 사전 자료가 기본 재배 방식 값으로 맞추고, 자동 검사가 그 문장을 확인한다. 계산은 `crop_kc_sets`만 쓴다.
- **v1 사전 자료 파일에서 계산 조건 부분을 뺐다.** v1.1에서 `kc_set_id`가 반드시 있어야 하므로, 예전 문장이 남아 있으면 다시 실행할 때 오류가 난다. "값을 고칠 때는 이 파일을 고치지 않는다"는 원칙의 예외로, 값이 아니라 구조 때문에 옮긴 것이다. 지금 DB에 있는 v1 계산 조건 20개는 v1.1 마이그레이션이 지운다(아직 물수지 자료가 붙기 전이라 안전).
- **Kc 기후보정은 croplib-dp가 한다.** 표값은 보정 전 값이고, 현장 PC처럼 지점의 생육 중기·후기 평균 풍속·최저습도로 FAO-56 식(62)(65) 보정을 한다.

## 확인한 것

- 임시 PostgreSQL에서 (가) 지금 Supabase와 같은 상태(v1 사전 자료까지 실행됨)에 새 파일을 실행하고, (나) 빈 DB에 모든 파일을 이름 순서대로 실행했다. 두 경우 모두 두 번 실행해도 오류가 없고 조건 50개, 기본 20개가 남았다.
- 비회원은 `crop_kc_sets`를 읽기만 되고 쓰기는 막힌다. 같은 조건(지점·작물·작형·재배 방식·토성·연도)을 두 번 넣으면 막힌다.

## 남은 것

- 물 화면(물5): 사과일 때 재배 방식 선택 칸. 주소에 남겨 다른 메뉴로 이어 준다(예: `?kc=3`).
- croplib-dp: 50개 조건 계산, Kc 기후보정, 업로드 전 검사.
- 배추는 재배 방식이 하나뿐이다. 태백 실측으로 보정한 값이 나오면 배추 2번을 더할 수 있다.
