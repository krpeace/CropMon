# 결정 0045: 이슈 기반 작업 흐름 — 계획 승인·검토·병합을 검토 채팅이 맡음

- 날짜: 2026-11-18
- 상태: 채택
- 관련 이슈: (이 PR)

## 배경

지금까지는 Claude 채팅이 쓴 지시문을 사용자가 작업창(Antigravity)에 붙여 넣고, 계획 승인·PR 확인·병합도 사용자가 했다. 사용자는 개발자가 아니어서 복사·붙여 넣기와 승인 대기가 일의 병목이 됐다. 회원제(2027-01-01)까지 셸 개편·로그인·내 농장 화면을 차례로 만들어야 하므로 이 흐름을 줄인다.

## 결정

1. 작업 지시는 GitHub 이슈(라벨 `작업지시`)로 낸다. 검토 채팅(Claude)이 이슈를 쓴다.
2. 작업창은 이슈를 직접 읽고, 계획을 이슈 댓글로 올리고, 승인 댓글을 확인한 뒤 진행한다. PR을 열고 완료 보고를 이슈 댓글로 남긴다. 절차는 `CLAUDE.md` "이슈 작업 흐름".
3. 계획 승인·PR 검토·병합은 검토 채팅이 한다. 병합 조건은 자동 검사 통과 + 검토. DB를 바꾸는 SQL이 있는 PR은 사용자가 SQL을 실행한 뒤 병합한다.
4. 같은 GitHub 계정을 쓰므로 댓글 첫머리 `[작업창]`·`[검토 채팅]`으로 쓴 쪽을 가른다.
5. 한 저장소의 지시는 한 채팅에서만 한다는 원칙은 그대로다. 지금은 이 검토 채팅이 CropMon 지시를 맡는다. 채팅을 바꿀 때는 새 채팅이 이어받았다고 이슈 댓글로 남긴다.

## 결과

- 사용자가 하는 일: 작업창에 "이슈 #번호 진행" 한 줄, 검토 채팅에 진행 확인, DB SQL 실행.
- 작업창이 댓글을 기다리는 동안 멈춰 있을 수 있다(최대 60분 확인 뒤 사용자에게 알림).

## 고침 (2026-11-18 밤) — 이슈를 이어서 자동으로

- 첫 하루를 돌려 보니 사용자가 끼어들어야 하는 곳이 셋이었다: ① 병합 뒤 작업창이 멈춰 새 이슈를 시작시키려면 사용자가 말해야 함 ② 작업창의 기다림(60분)이 검토 채팅의 확인 간격보다 짧아 먼저 멈춤 ③ 검토 채팅은 예약 확인 때만 움직임.
- 그래서 작업창은 병합을 확인하면 **다음 `작업지시` 이슈를 스스로 찾아 시작**하고(흐름 10), 기다림은 **120분**으로 늘린다(흐름 3 · 7 · 10). 검토 채팅은 작업이 도는 동안 약 30분 간격으로 확인한다. 사용자는 작업창을 처음 한 번만 시작시킨다.

## 고침 (2026-11-19) — 검토 채팅 쪽 규칙을 `docs/WORKFLOW.md`로

- 검토 채팅의 규칙(맡는 일 · 이슈 쓰는 법 · 도구 · 예약 확인 · 새 채팅으로 넘기기)을 저장소 `docs/WORKFLOW.md`에 둔다. 작업창 단계는 `CLAUDE.md`에 그대로 두고 다시 적지 않는다(두 곳이 어긋나지 않게).
- `CLAUDE.md`가 아닌 까닭: 작업창이 매번 자동으로 읽는 파일이라 검토 채팅 규칙을 넣으면 읽을 글만 는다. Claude 프로젝트 문서가 아닌 까닭: 검토 채팅은 처음에 저장소를 받으므로 따로 찾을 필요가 없고, 고친 기록이 git에 남으며, croplib-dp도 같은 자리(`docs/WORKFLOW.md`)를 쓴다.
- 넘길 때의 "지금 상태"만 Claude 프로젝트의 인계서에 둔다.
- 새 채팅으로 넘기는 기준을 숫자로 정했다(병합 PR 5개 · 예약 확인 8번 · 12시간 · 이정표 끝). 첫 검토 채팅(11/18~19)이 PR 10개 · 예약 확인 10여 번 뒤에 넘긴 경험에서.
