# 데이터 계약 (DATA_CONTRACT)

계산 저장소(croplib-dp, Python)가 Supabase에 올리는 자료와, 이 웹이 읽는 자료의 약속입니다. 테이블을 바꾸면 이 문서와 `supabase/migrations/`를 같은 PR에서 고치고 버전을 올립니다. `src/infra/supabase/contract.test.ts`가 이 문서의 테이블 목록과 마이그레이션이 같은지 자동으로 검사합니다.

## 현재 버전: v2.2 (2026-11-20)

## 공통 규칙

- **이름:** 영문 소문자와 밑줄. 단위가 있는 값은 이름 끝에 단위를 붙입니다 (`eto_mm`, `tmax_c`, `rh_mean_pct`). 화면이 단위를 추측할 필요가 없게 하려는 것입니다.
- **날짜와 시각:** 날짜는 한국 날짜(`date`), 시각은 시간대 포함(`timestamptz`)입니다.
- **결측:** 값이 없으면 빈 칸(null)으로 두고 0을 넣지 않습니다. 화면은 null을 "자료 없음"으로 보여 줍니다. 채운 값은 `filled = true`로 표시해 "추정 포함" 등을 구분합니다.
- **한계 (기상청 사후 정정·철회):** 기상청이 뒤늦게 관측 값을 거둬들이거나 정정한 날의 옛 값이 DB에 남아 있으면, 화면의 최신 기준 날짜가 실제 관측과 하루 정도 어긋날 수 있습니다.
- **계산 버전:** 계산 결과에는 `calc_version`(croplib-dp 버전)을 남겨, 식을 고친 뒤에도 어느 계산으로 나온 값인지 알 수 있게 합니다.
- **권한:** 모든 테이블에 RLS를 켭니다. **공개 표**는 비회원(`anon`)과 회원(`authenticated`) 누구나 읽기만 가능하고, 쓰기는 croplib-dp의 서버 키(service role)만 합니다. **회원 표**(`members`, v2.0)는 **자기 줄만** 읽고 정해진 열만 고칠 수 있으며, 비회원에게는 아무 권한이 없습니다(서버 키는 지금처럼 RLS를 건너뜁니다). 서버 키는 이 저장소의 화면 코드에 넣지 않습니다. **농장 표**(v2.1)도 회원 표와 같은 원칙입니다 — `farms` · `irrigation_logs`는 회원 본인이 읽기 · 쓰기 · 지우기(정해진 열만), `farm_seasons` · `farm_calc_status` · `farm_water_*`는 회원 본인 읽기만이고 쓰기는 서버 키(`farm_seasons`는 `sync_farm_seasons`)입니다. 다른 회원의 줄은 보이지 않습니다.
- **값의 범위:** 범위 검사(예: ETo 0~15 mm/d)는 croplib-dp가 올리기 전에 합니다. DB는 키, 연결, 이름이 정해진 칸처럼 구조만 막습니다. 범위 규칙을 고칠 때 DB를 바꾸지 않아도 되게 하려는 것입니다.
- **원자료:** 시각별 예보와 API 응답 원문은 DB가 아니라 Storage의 비공개 버킷 `raw`에 압축해 둡니다(v1.2에서 버킷을 만듦). 비회원·회원은 읽을 수 없고, croplib-dp의 서버 키만 씁니다. 위치는 `forecast_runs.raw_path`에 남깁니다.
- **2계층:** FAO-56 표준값(`crops`, `crop_seasons`, `crop_kc_sets`, `soil_types`)과 농장별 보정값(v2의 `crop_overrides`)을 따로 둡니다. 사용자가 고친 작기 시작일도 보정값 층에 저장하고, 표준값은 바꾸지 않습니다.

## 토양수분 상태 판정

`water_balance_daily`와 `water_outlook`의 `status`에는 아래 코드를 저장합니다. 화면 이름은 `src/domain/water-status.ts`가 붙입니다. 서비스 엑셀과 같은 기준이며, 위에서부터 차례로 판정합니다.

| 코드      | 토양수분 상태 | 조건                             | 판정하는 날      |
| --------- | ------------- | -------------------------------- | ---------------- |
| `dormant` | 휴면기        | 생육기 밖 (Kc ≤ 0)               | 관측·예보        |
| `wet`     | 과습          | 생육기이고 Dr이 0 (0.05 mm 미만) | 관측 물수지 날만 |
| `normal`  | 보통          | 0 < Dr < 여유 기준               | 관측·예보        |
| `caution` | 주의          | 여유 기준 ≤ Dr < RAW             | 관측·예보        |
| `need`    | 관수 필요     | Dr ≥ RAW                         | 관측·예보        |

- **여유 기준:** 지금은 RAW × 0.5입니다.
- **과습은 관측 물수지 날만 판정합니다.** 예보로 진행한 날(`water_outlook`)에는 과습을 판정하지 않으므로, 이 표의 `status`에는 `wet`이 들어갈 수 없습니다.
- 이 기준은 이론 근거가 아직 약해서 서비스를 운영하면서 다듬습니다. 판정 규칙과 여유 기준은 croplib-dp 계산 코드에 있고, 바꾸면 `calc_version`을 올려 어느 규칙으로 낸 판정인지 남깁니다. 코드 이름이 그대로면 테이블 구조는 바뀌지 않습니다.
- 디자인 시안의 "아직 여유"는 주의(`caution`), "토양 수분 충분"은 보통(`normal`), "과습 경고"는 과습(`wet`)입니다. 시안의 예시 값(춘천 사과 Dr 31 / RAW 35 → 주의, 태백 사과 Dr 9 / RAW 35 → 보통)이 이 기준과 맞습니다.
- 3일 전망 요약(`status_start`)의 휴면기는 회차 발표 날짜(한국 날짜)의 Kc로 판정합니다. 작기 마지막 다음 날 아침에 관수를 권하거나, 작기 첫날 아침에 휴면기로 나오는 하루 어긋남을 막기 위해서입니다 (croplib-dp 결정 0015).

## 흙 물 상태 판정 (작물 공통)

`soil_water_daily`의 `status`에는 아래 코드를 저장합니다. 화면 이름은 이 표를 따릅니다. 위에서부터 처음 맞는 것으로 판정하며, 판정은 croplib-dp가 하고 화면은 이름만 붙입니다. 작물용 `status`(`need`, `caution`, `normal`, `wet`, `dormant`)와는 **섞지 않습니다** (표가 다르고 코드도 다릅니다).

| 코드       | 화면 이름 | 조건                                                           |
| ---------- | --------- | -------------------------------------------------------------- |
| `winter`   | 겨울철    | 12~2월 (판정 안 함)                                            |
| `pool`     | 물 고임   | 그날 끝 Dr = 0 (0.05 mm 미만) 이고, 그날 또는 전날 `dp_mm` ≥ 1 |
| `ample`    | 충분      | `aw_pct` ≥ 80                                                  |
| `fair`     | 보통      | 60 ≤ `aw_pct` < 80                                             |
| `dry`      | 건조      | 30 ≤ `aw_pct` < 60                                             |
| `very_dry` | 매우 건조 | `aw_pct` < 30                                                  |

- 60%는 RAW 경계(p = 0.40), 30%는 증발산이 절반으로 줄어드는 점(Ks = 0.5)입니다. 80%는 화면 구분용입니다.
- 비가 없으면 건조까지 남은 날(`days_to_dry`)은 `fair`일 때만 채웁니다.

### `public.scenarios`

대표 계산 조건입니다. 물수지는 지점만으로 정해지지 않고 작물, 작형, 토성, 작기 시작일에 따라 달라집니다. 그래서 "어떤 조건으로 계산했나"를 한 줄로 남기고, 물수지 테이블은 이 줄을 가리킵니다. 토성 12종 선택을 나중에 열 때도 이 표에 줄만 늘리면 됩니다.

| ---------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| `scenario_id`                | 문자, 키 | "101-apple-main-k3-loam-2026" (지점-작형-k재배 방식 번호-토성-연도)                                                    |

| `crop_id`                    | 문자     | `crops`를 가리킴                                                                                                       |
| `season_type_id`             | 문자     | `crop_seasons`를 가리킴                                                                                                |
| `kc_set_id`                  | 문자     | `crop_kc_sets`를 가리킴 (v1.1)                                                                                         |
| `soil_code`                  | 문자     | `soil_types`를 가리킴                                                                                                  |
| `season_year`                | 정수     | 작기 연도                                                                                                              |
| `season_start`, `season_end` | 날짜     | 그해 생육기 시작·끝. 시작 = 작형의 기본 시작일, 끝 = 시작 + 생육단계 일수 합. 밖은 휴면기                              |

- **2027 포도 공개 계산 조건 194줄**(v2.1): 운영 97곳 × 작형 둘 × `grape-k1` × 양토. 비가림 2027-04-20 ~ 2027-11-10(205일), 시설가온 2027-01-01 ~ 2027-07-09(190일, 시작 미정 대신 1월 1일). TAW 130, RAW 45.5, `dr0_mm` 0, 두 작형 모두 기본 조건. 이름은 `101-grape-rainshelter-k1-loam-2027`. 이 줄이 들어가면 croplib-dp 물수지 수집기가 2027-01-01부터 시설가온을 계산하기 시작하는데, croplib-dp가 시설 재배(비 0)와 `etc_only`를 반영하기 전이면 값이 틀리게 써질 수 있습니다. 포도는 G1 전까지 화면에 안 나오고 croplib-dp가 고친 뒤 다시 씁니다. 2027년 기본 조건은 모두 사과 97 + 배추 97 + 포도 194 = 388줄입니다.
- 공개 조건은 대표 밖 87곳 시드 마이그레이션(`20261110000000_seed_scenarios_non_rep.sql`, 아래 기록표 참고) **실행 전**에는 연도별 50개(기본 조건 20개)이고, **SQL 실행 뒤**에는 대표 10곳 × 5조건 = 50개와 대표 밖 87곳 × 기본 2조건(사과 k3, 배추 k1) = 174개를 합쳐 **연도별 총 224개(기본 조건은 10×2 + 87×2 = 194개)**입니다 (#103, 결정 0042). 대표 밖 지점은 기본 재배 방식만 제공하며, 화면에서 비기본 재배 방식을 고르면 가까운 대표 지점 안내를 보여 줍니다.
- 사용자가 시작일을 고치는 기능은 1/1 회원 버전부터 엽니다. 고친 값은 보정값 층(v2)에 저장하고, 서버가 다음 수집 회차에 다시 계산합니다. 11/06 비회원 화면은 기본값으로 고정합니다.

#### 새해 계산 조건 등록 절차

croplib-dp 물수지 수집기는 `scenarios`를 읽기만 하고 새로 만들지 않으므로, 해마다 연말에 새해 조건 줄을 미리 넣어 둡니다(구조·의미 변경이 아니라서 데이터 계약 버전은 올리지 않음). 화면과 croplib-dp 모두 `season_year`로 걸러 읽으므로 12월 전에 넣어도 화면이 새해로 미리 바뀌지 않습니다.

1. **12월 중순까지(늦어도 12/31)** 새 마이그레이션 `supabase/migrations/YYYYMMDD000000_seed_scenarios_<새해>.sql`을 더합니다. 전년 시드 파일을 복사해 `scenario_id` 끝의 `-<전년>`, `season_year`, `season_start`·`season_end`의 연도만 `<새해>`로 바꿉니다.
   - 날짜 주의: 작기 시작이 3/1 이전인 작형이 생기면 윤년에 끝 날짜를 생육단계 일수로 다시 계산합니다(지금 작형인 사과 4/1·여름배추 7/1 시작은 윤년이어도 시작·끝 날짜가 같음).
2. `src/infra/supabase/seed.test.ts`에 `describeAnnualScenarios(<새해>, ...)` 시험을 더해 전년 줄과 맞대어 연도만 다른지 확인합니다.
3. 서울 DB의 SQL Editor에서 적용 전후 조회로 줄 수와 값을 확인합니다:
   ```sql
   -- (1) 적용 전후 연도별 줄 수 확인 (대표 10곳만 있을 때는 n = 50, n_default = 20 / 대표 밖 87곳 시드 SQL 실행 뒤에는 n = 224, n_default = 194)
   select season_year, count(*) as n, count(*) filter (where is_default) as n_default
   from public.scenarios group by 1 order by 1;

   -- (2) 마이그레이션 파일 내용 전체 붙여 넣고 Run

   -- (3) 값 비교: 0줄이어야 함 (전년과 연도만 다르고 나머지가 같은지, 예: 2026 → 2027)
   select a.scenario_id
   from public.scenarios a
   left join public.scenarios b
     on b.scenario_id = replace(a.scenario_id, '-2026', '-2027')
    and b.season_year = 2027
    and b.stn_id = a.stn_id and b.crop_id = a.crop_id and b.season_type_id = a.season_type_id
    and b.kc_set_id = a.kc_set_id and b.soil_code = a.soil_code
    and b.dr0_mm = a.dr0_mm and b.taw_mm = a.taw_mm and b.raw_mm = a.raw_mm
    and b.is_default = a.is_default
    and b.season_start = (a.season_start + interval '1 year')::date
    and b.season_end = (a.season_end + interval '1 year')::date
   where a.season_year = 2026 and b.scenario_id is null;
   ```
4. **1월 1일 오후 운영 확인**: 물 화면(사과·배추)에 `"이 지역·작물의 <새해> 계산 조건이 아직 없어요."`가 뜨지 않는지 확인합니다(사과는 4/1, 배추는 7/1부터 작기가 시작되므로 1월에는 물 계산 줄이 없는 것이 정상).

| 열                                                       | 형식            | 뜻                                                                                                          |
| -------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------- |
| `stn_id`                                                 | 문자            | `stations`를 가리킴                                                                                         |
| `t_base_c`                                               | 수              | 기준온도(℃). **-10 ~ 30** (`crops.t_base_c`와 같은 범위). 키의 일부(숫자)라 `4`와 `4.0`은 **같은 키**       |

- **누적 시작 전 날은 줄이 없습니다**(croplib-dp 회신, 결정 0063): 계열마다 **그해 누적 시작일 ~ 12-31 줄만** 씁니다. 예) (10, 04-20) 계열은 04-20 ~ 12-31. 그 안의 누적 · 평년 누적 · 며칠 빠른가는 모두 그 누적 시작부터 셉니다. **화면은 그 계열에 줄이 없는 날을 "작기 전"으로 봅니다**(3단계 화면 작업 때 쓰는 규칙). 01-01 계열은 지금처럼 1년 내내 줄이 있습니다.
- **`t_base_c`의 형식**: `numeric`(자릿수 없음, **실수형(float) 아님**)입니다. 사전 `crops.t_base_c`와 옛 `heat_daily.t_base_c`가 모두 `numeric`이라 뷰 · 새 표 · 옛 표가 같은 형식이고, `numeric(4,1)`처럼 자릿수를 묶으면 4.55 같은 값이 말없이 반올림되므로 묶지 않습니다. **숫자로 비교하므로 `4` · `4.0` · `4.00`은 같은 키이고 4.5는 그대로 4.5입니다.** 응답에 `4`와 `4.0`이 섞여 보일 수 있으니 **문자열로 비교하지 말고 숫자(Decimal)로 비교합니다.** croplib-dp는 뷰의 `heat_t_base_c` 값을 그대로 보내면 됩니다.
- **해를 넘는 누적 시작**(예: 12-01 시작 계열)은 1/1 계열에 없습니다. 그때 "작기 해" 열이 필요한지는 **그때 정합니다**(지금 열을 만들지 않았습니다).

| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `crop_id`             | 작목. 작물 공통은 `common`                                                                                                          |
| `season_type_id`      | 작형. 작물 공통은 비어 있음                                                                                                         |
| `heat_t_base_c`       | 적산온도 계열의 기준온도 = `crops.t_base_c`. **적산온도를 내지 않으면 비어 있음**                                                   |
| `heat_cum_start_mmdd` | 적산온도 계열의 누적 시작 = `crop_seasons.cum_start_mmdd`. **비어 있으면 적산온도를 내지 않음**(포도 시설가온). 위와 함께 비거나 참 |
| `sun_cum_start_mmdd`  | 적산일사 계열의 누적 시작 = `coalesce(crop_seasons.cum_start_mmdd, '01-01')`. 작물 공통 · 시설가온(미정)은 `01-01`                  |

- **줄**: **단계 일수 네 개(`l_ini_d` · `l_dev_d` · `l_mid_d` · `l_late_d`)가 모두 있는 작형마다 한 줄** + **작물 공통** 한 줄입니다(D1-2와 같은 기준 — `cum_start_mmdd`가 비었는지로 거르면 적산온도는 비우지만 일사 계열은 있는 시설가온이 빠집니다). 지금 5줄: `apple-main` · `kimchi_cabbage-summer` · `grape-rainshelter` · `grape-heated` · `common`(값이 빈 배추 봄 · 가을 · 월동은 없음). 작물 공통의 기준온도는 `crops`의 `common` 줄(5, 결정 0020), 누적 시작은 작형이 없어 `01-01` 고정입니다.
- **1/1 계열**(확인 SQL이 못 박음): 적산온도 **(4, 01-01)**(사과) · **(5, 01-01)**(배추 · 작물 공통) · **(10, 04-20)**(포도 비가림), 적산일사 **01-01**(사과 · 배추 · 작물 공통 · 시설가온) · **04-20**(포도 비가림). 포도 시설가온은 적산온도를 내지 않고 일사만 01-01입니다.
- **계산할 계열 = 이 뷰의 `distinct (heat_t_base_c, heat_cum_start_mmdd)`(둘 다 빈 줄은 제외)와 `distinct sun_cum_start_mmdd`** 입니다.

#### 적산 계열은 세 단계로 바꿉니다 (결정 0063)

1. **CropMon이 새 표 · 뷰를 넣는다 — v2.2.** 옛 `heat_daily` · `sun_daily`는 **한 글자도 바꾸지 않습니다**(croplib-dp가 계속 옛 키로 써도, 지금 화면이 옛 표를 읽어도 아무것도 안 깨집니다).
2. croplib-dp가 새 표에도 쓰기 시작합니다(croplib-dp 이슈).
3. CropMon 화면이 새 표로 읽기를 바꾸고 **옛 표 · 옛 줄은 3단계에서 지웁니다**(D1-3 2단계). 시점은 CropMon이 알립니다.

2단계가 시작된 뒤에는 v2.2의 되돌리기 SQL이 새 표에 줄이 있으면 멈춥니다(쓴 값이 사라지고 croplib-dp 쓰기가 실패하므로).

### `public.soil_water_daily`

| ------------------------------------ | --------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------- |

- **고칠 수 있는 열(열 단위 권한):** `display_name`, `terms_version`, `terms_agreed_at`, `privacy_version`, `privacy_confirmed_at`, `age14_confirmed_at`, `layout`, `font_scale`, `theme`. `user_id`·`provider`·`role`·`role_verified_at`·`created_at`·`updated_at`은 회원이 바꿀 수 없습니다.
- **가입 트리거:** `auth.users`에 줄이 생기면(`on_auth_user_created`, after insert) 보안 정의 함수 `public.handle_new_user()`가 `members`에 한 줄을 넣습니다(`user_id`, `display_name`, `provider`). **이 트리거는 오류를 내지 않습니다** — 오류가 나면 그 사람은 로그인 자체가 막히기 때문입니다. 이름·공급자는 내부 함수 `public.member_seed()`가 골라 모르면 비워 두고, 그래도 생길 수 있는 오류는 경고만 남기고 넘어갑니다(줄이 빠지면 로그인 직후 `ensure_my_member()`가 만듭니다). 직접 부를 수 없습니다(실행 권한 없음).

### `ops.withdrawn_accounts`

탈퇴 기록입니다 (v2.0). 공개 표가 아니라 `ops` 스키마(비회원·회원이 볼 수 없는 운영용)에 있고, RLS를 켠 채 정책이 없어 서버 키만 읽고 씁니다. 백업에서 되살릴 때 그 사이 탈퇴한 회원을 다시 지우기 위한 작은 기록이며, 7일 지난 줄 지우기는 정리 작업(O2)이 합니다.

### 회원 함수: `public.delete_my_account()` · `public.ensure_my_member()`

둘 다 보안 정의 함수이며 인자를 받지 않습니다(남의 번호를 넘길 길이 없음). 회원(`authenticated`)만 실행하고 비회원(`anon`)은 못 합니다.

- **`public.delete_my_account()`:** 회원 본인이 탈퇴합니다. ① `ops.withdrawn_accounts`에 위 해시 한 줄(이미 있으면 시각만 갱신) ② `auth.users`의 자기 줄 삭제 → `members`가 연쇄로 지워집니다(v2.1의 농장 표들도 같은 연쇄). 비회원이 부르면 오류. 카카오·네이버·구글 연결 끊기는 서버 키가 필요해 따로 서버 쪽 함수(L6)가 합니다.
- **`public.ensure_my_member()`:** 줄이 빠진 회원이 자기 줄을 만듭니다. 가입 트리거와 같은 식(`member_seed()`)으로 자기 `auth.users` 줄에서 이름·공급자를 읽어 `members`에 넣고, 이미 있으면 아무것도 하지 않습니다(두 번 불러도 오류 없음). 로그인 직후 한 번 부르는 것이 약속입니다(L2). **로그인 콜백(`/auth/callback`, 이슈 #182, 결정 0061)이 로그인 직후 한 번 부릅니다 — 실패해도 로그인은 계속됩니다.** (계약 판 번호는 올리지 않습니다: 함수는 그대로이고 부르는 곳만 생겼습니다.)
- **확인 SQL:** `supabase/checks/d1_1_members_check.sql`(실행하면 아무것도 남지 않음, 맨 끝 `all_ok = true`). 되돌리기 SQL은 `supabase/checks/d1_1_members_rollback.sql`(실행하지 않음).

| `season_type_id`      | 문자, 비어도 됨 | 작형. **작물 공통이면 비우고, 아니면 필수**, **그 작목의 작형**이어야 한다(합성 외래키 `(season_type_id, crop_id)`) |

| `season_start_mmdd`   | 문자, 비어도 됨 | 시작 "MM-DD". 비어 있으면 **미정**. **실제 있는 날만**(02-29 · 04-31 거절). 작물 공통이면 늘 비움                   |
| `season_start_source` | 문자, 비어도 됨 | `default` / `user`. 시작일이 미정이면 비어 있다(둘은 함께 비거나 함께 찬다)                                         |
| `season_end_mmdd`     | 문자, 비어도 됨 | 끝 "MM-DD". **1/1에는 화면이 받지 않아 늘 비어 있고, 값이 있어도 끝 계산에 쓰지 않는다** (나중 판의 규칙)           |
| `created_at`          | 시각            | 만든 시각. 회원이 못 고친다                                                                                         |
| `updated_at`          | 시각            | 고친 시각 (트리거). 회원이 못 고친다                                                                                |

- 회원이 못 고치는 열(`farm_id` · `user_id` · `created_at` · `updated_at`)은 **열 단위 권한**으로 막습니다(`members`와 같은 방식).
- 작물 설정 열(`crop_id` · `season_type_id` · `kc_set_id` · `season_start_mmdd` · `season_end_mmdd`)이 바뀌거나 농장이 처음 생기면 트리거가 `sync_farm_seasons`로 작기 줄(`farm_seasons`)을 맞춥니다. 지점 · 토성 · 면적이 바뀌면 지금 작기 줄의 시작일부터 다시 계산을 요청합니다(아래 "농장 함수 · 트리거").

### `public.farm_seasons`

날짜가 정해진 작기 줄입니다(v2.1). **회원은 읽기만** 하고, 줄은 `sync_farm_seasons`만 쓰고 지웁니다. croplib-dp는 읽기만 합니다.

| 열                                       | 형식          | 뜻                                                                               |
| ---------------------------------------- | ------------- | -------------------------------------------------------------------------------- |
| `farm_season_id`                         | 고유 번호, 키 | 작기 줄 번호                                                                     |
| `farm_id`                                | 고유 번호     | `farms`를 가리킴 (농장이 지워지면 함께 지워짐)                                   |
| `crop_id`, `season_type_id`, `kc_set_id` | 문자          | 줄을 만들 때의 `farms` 값 (`kc_set_id`는 비어도 됨). 합성 외래키로 작목과 맞는다 |
| `start_date`, `end_date`                 | 날짜          | 작기 시작 · 끝(포함). 끝이 다음 해여도 된다                                      |
| `start_unset`                            | 참/거짓       | 시작이 미정이라 **1월 1일로 대신한** 줄                                          |
| `created_at`, `updated_at`               | 시각          | 만든 · 고친 시각                                                                 |

- 같은 농장의 날짜 범위는 **겹칠 수 없습니다**(배제 제약 `farm_seasons_no_overlap`, `btree_gist` 필요). `end_date >= start_date`이고 작기는 시작일 포함 **366일 이하**입니다.
- **"지금 줄"의 정의는 한 곳**(`public.farm_current_season`): 끝이 오늘 이후(`end_date >= 오늘`, **끝나는 날 당일은 아직 작기 중**)인 줄 가운데 시작이 가장 이른 줄 = 작기 중이거나 아직 시작 전인 가장 가까운 줄. 작기 줄 만들기와 관수 기록 날짜 규칙이 이 정의를 같이 씁니다.
- 지난 줄(끝이 오늘 전)은 "작기 끝" 판정 · 지난 작기 돌아보기에 쓰므로 남깁니다(고치지 않음, 겹칠 때만 아래 규칙으로 끝을 자름).

### `public.irrigation_logs`

관수 기록입니다(v2.1). **회원 본인이 읽기 · 쓰기 · 지우기**를 합니다. **mm는 저장하지 않습니다**(톤으로 넣은 값도 L로 저장). 하루에 여러 줄을 넣을 수 있습니다.

| 열                         | 형식            | 뜻                                              |
| -------------------------- | --------------- | ----------------------------------------------- |
| `log_id`                   | 고유 번호, 키   | 기록 번호. 회원이 못 정한다                     |
| `farm_id`                  | 고유 번호       | `farms`를 가리킴. 넣을 때만 정하고 고칠 수 없다 |
| `date`                     | 날짜            | 관수한 날(한국 날짜)                            |
| `volume_l`                 | 수              | 양(L). **0보다 큼**. 톤 입력은 ×1,000으로 저장  |
| `input_unit`               | 문자            | 입력한 단위 `L` / `ton`                         |
| `memo`                     | 문자, 비어도 됨 | 메모 (500자까지)                                |
| `created_at`, `updated_at` | 시각            | 만든 · 고친 시각                                |

- **날짜 규칙(DB가 지킨다)**: 넣을 때는 그 농장의 **지금 작기 줄 시작일 ~ 오늘(한국 날짜)** 안만 됩니다. 미래 · 작기 밖 · 작기 줄이 없는 농장(작물 공통) · 작기 시작 전 줄만 있는 때는 거절합니다. 고칠 때는 **날짜(나 농장)가 바뀔 때만** 같은 검사를 합니다(작기 시작일을 바꿔 작기 밖이 된 기존 기록의 메모 · 양은 고칠 수 있음). **지우기는 언제나 됩니다.** 작기 시작일을 바꿔 작기 밖이 된 기존 기록은 지우지도 막지도 않습니다.

### `public.farm_calc_status`

농장 하나 = 한 줄인 다시 계산 상태입니다(v2.1). **회원은 읽기**, croplib-dp(서버 키)는 읽기 · 쓰기입니다. 농장이 생길 때 트리거가 빈 줄을 만듭니다. 화면의 "계산 반영 중" = `requested_at > done_at` 또는 `done_at` 없음(화면은 W1).

| 열             | 형식            | 뜻                                                                                           |
| -------------- | --------------- | -------------------------------------------------------------------------------------------- |
| `farm_id`      | 고유 번호, 키   | `farms`를 가리킴                                                                             |
| `requested_at` | 시각, 비어도 됨 | 다시 계산을 요청한 시각 (트리거가 씀)                                                        |
| `recalc_from`  | 날짜, 비어도 됨 | 이 날부터 다시 계산 (트리거가 씀. 기다리는 중에는 더 이른 날로만 당겨진다)                   |
| `done_at`      | 시각, 비어도 됨 | 끝낸 시각. **croplib-dp 는 "읽기 시작한 시각"을 쓴다** (끝난 시각이면 그 사이 요청이 묻힌다) |
| `result`       | 문자, 비어도 됨 | `ok` / `failed`                                                                              |
| `error`        | 문자, 비어도 됨 | 사람이 읽는 말. **개인 값 · 위치 · 키 없음**                                                 |
| `calc_version` | 문자, 비어도 됨 | 계산 버전                                                                                    |

- **누가 쓰는 열인지**: croplib-dp 가 쓰는 열 — `done_at` · `result` · `error` · `calc_version`. 트리거가 쓰는 열 — `requested_at` · `recalc_from`. 서버 키(service role)는 RLS를 건너뛰므로 croplib-dp 의 쓰기에는 따로 권한 설정이 필요 없습니다. 회원은 이 표를 읽기만 합니다.

### 농장 함수 · 트리거 · 깨우기 (v2.1)

**날짜 규칙(물수지 · 판정 계산이 아니라 날짜 계산입니다).** 연도 규칙은 `public.farm_season_window(S, L, 오늘)` **한 곳**입니다.

- S = 시작 월-일(미정이면 `01-01`이고 그 줄은 `start_unset = true`), L = 작형의 단계 일수 합(`l_ini_d + l_dev_d + l_mid_d + l_late_d`). 오늘이 [작년 S, S + L) 또는 [올해 S, S + L) 안이면 그 작기, 아니면 **다음에 올 S**. 끝 = 시작 + L − 1.
- 예) 포도 시설가온 S = 12-01, L = 190: 2026-11-17 → 다음 작기 2026-12-01 ~ 2027-06-08, 2027-02-10 → 2026-12-01 시작 작기 중(끝 2027-06-08), 끝나는 날 당일(2027-06-08)도 작기 중, 다음 날부터는 2027-12-01 ~ 2028-06-07.

**`public.sync_farm_seasons(farm_id)`** — 날짜 줄 만들기 · 고치기. 부르는 곳: ① `farms`가 생길 때와 작물 설정 열이 **실제로 바뀔 때만** 트리거로 ② croplib-dp 02시 정기 회차가 모든 농장에 대해(서버 키). **서버 키만 실행**하고 회원 · 비회원은 직접 못 부릅니다(남의 농장 번호를 넣는 길이 없게). 날짜를 인자로 받는 안쪽 함수 `sync_farm_seasons_at(farm_id, 오늘)`은 아무도(서버 키도) 직접 못 부르고 확인 SQL이 날짜를 바꿔 시험할 때 씁니다.

- 지금 줄이 있으면 **고쳐 씁니다**(시작일을 바꿔도 새 줄을 만들지 않음). 지금 줄이 없으면(마지막 줄이 오늘 전에 끝났으면) 다음 작기 줄을 **만듭니다**.
- 오늘보다 앞에 끝난 줄은 **고치지 않고 남깁니다**(지난 작기). 단 새 줄과 겹치면 **지난 줄의 끝을 새 줄 시작 전날로 자르고**, 통째로 새 줄 안에 들어가면 지웁니다. 예) 사과 지난 줄 2026-04-01 ~ 10-27이 있고 오늘 11-20에 시설가온 시작을 10-01로 고르면 새 줄은 2026-10-01 ~ 2027-04-08이고 사과 줄은 2026-04-01 ~ 09-30으로 줄어듭니다. 자른 기간은 새 줄 시작일부터 다시 계산됩니다.
- **작물 공통** 농장은 줄을 만들지 않고, 끝이 오늘 이후인 줄(지금 · 앞으로)은 지우며 지난 줄은 남깁니다.
- `season_end_mmdd`는 끝 계산에 쓰지 않습니다(끝은 늘 위의 식). 단계 일수가 빈 작형을 고른 농장은 저장이 거절됩니다.

**다시 계산 요청(`public.touch_farm_calc`)** — `farm_calc_status` 줄을 만들거나 고칩니다(`requested_at`, `recalc_from`). 기다리는 중(`requested_at > done_at` 또는 `done_at` 없음)이면 `recalc_from`을 **더 이른 날로만** 당기고, 끝난 뒤의 새 요청이면 새 날로 시작합니다.

| 바뀐 것                                            | `recalc_from`                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------ |
| 관수 기록 넣기 · 지우기                            | 그 기록의 날                                                       |
| 관수 기록 고치기 (날짜 · 양 · 단위가 바뀔 때만)    | 옛 날과 새 날 중 이른 날                                           |
| 작기 줄 시작일 변경 · 작목 · 작형 · 재배 방식 변경 | 옛 시작일과 새 시작일 중 이른 날 (끝이 오늘 이후인 줄이 바뀔 때만) |
| 새 작기 줄 만들기 (지난 줄을 자른 경우 포함)       | 새 줄의 시작일                                                     |
| 지점 · 토성 · 면적 변경                            | 지금 작기 줄의 시작일 (지금 줄이 없는 작물 공통은 요청하지 않음)   |

**깨우기** — 요청을 기록하면 croplib-dp 농장 계산 작업을 깨웁니다: `ops.dispatch_workflow('farm_calc.yml')`. 관수 기록을 연달아 넣어도 작업이 줄줄이 뜨지 않게 **2분 창**을 둡니다(`ops.farm_calc_wake.last_wake_at`이 2분 안이면 다시 안 부름). 도는 작업이 못 본 요청을 놓치지 않도록 **매분 보충 예약**(`pg_cron` 작업 `croplib-farm-calc-sweep`, `ops.farm_calc_sweep()`)이 "마지막 깨우기 **뒤에** 들어온 기다리는 요청"이 있고 마지막 깨우기가 2분 지났을 때 한 번 더 깨웁니다(기다리는 요청이 없으면 색인 한 번 조회로 끝나고, 이미 깨웠던 요청으로는 반복해서 부르지 않습니다). **깨우기가 실패해도(토큰 없음 · 작업 파일 없음 404 · 네트워크) 회원의 저장은 성공합니다.** 작업 파일이 아직 없으면 GitHub이 404를 돌려주고 `ops.dispatch_recent`에 남을 뿐입니다.

**깨우기 스위치 — 기본은 꺼짐.** `ops.farm_calc_wake.enabled`(기본 `false`)가 꺼져 있으면 저장 트리거도 매분 보충 예약도 `ops.dispatch_workflow`를 부르지 않고 `last_wake_at`도 바꾸지 않습니다. **다만 `farm_calc_status`의 `requested_at` · `recalc_from` 기록은 스위치와 상관없이 늘 합니다**(croplib-dp 정기 계산이 따라잡습니다). croplib-dp 에 `farm_calc.yml`이 아직 없는 동안 부르면 `net.http_post` 404가 조용히 묻히므로, **그 파일이 병합된 뒤** 사용자가 SQL Editor 에서 켭니다:

```sql
update ops.farm_calc_wake set enabled = true;
```

끄려면 `enabled = false`입니다. 판단 함수 `ops.farm_calc_wake_due(지금, 마지막 깨우기, 기다리는 요청 있음, 보충 예약인가, 스위치)`가 꺼짐이면 늘 거짓을 돌려줍니다(확인 SQL이 판단표로 시험).

**정기(02시 · 17시) 농장 계산은 CropMon 예약(cron)이 아닙니다.** croplib-dp 가 `collect.yml`이 끝난 뒤 이어서 부릅니다. CropMon 에 있는 예약은 `croplib-farm-calc-sweep`(매분) 하나이고, 이것은 **회원 저장 깨우기를 보충**할 뿐 정기 계산을 대신하지 않습니다.

**`public.sync_all_farm_seasons()`** — 모든 농장에 대해 안쪽 `sync_farm_seasons_at(farm_id, 한국 오늘)`을 부르고 **처리한 농장 수**(정수)를 돌려줍니다. **서버 키(`service_role`)만 실행**합니다(`sync_farm_seasons`와 같음). croplib-dp 가 정기 계산 **전에 한 번** 부르면 되고(끝난 작기의 다음 줄 만들기 · 지난 줄 자르기), 한 농장이 실패해도(예: 단계 일수가 비게 바뀐 작형) 전체가 멈추지 않도록 농장마다 따로 처리하고 실패한 농장은 세지 않습니다(경고에는 오류 번호만).

**croplib-dp와의 약속** (결정 0062): ① 작업 파일 이름은 `farm_calc.yml` — 그 파일이 병합된 뒤 사용자가 위 켜는 SQL을 실행한다(그 전에는 깨우기가 꺼져 있다) ② `done_at`에는 **읽기 시작한 시각**을 쓴다 ③ **정기(02시 · 17시) 계산은 croplib-dp 가 `collect.yml` 뒤에 이어서 부른다** — 그 전에 서버 키로 `public.sync_all_farm_seasons()`를 한 번 부른다(CropMon cron 이 아님) ④ 시설 재배 작형(`crop_seasons.is_protected`)은 비를 0으로 계산하고, 쓰는 물인 날은 `status = 'etc_only'`로 올린다 ⑤ `crop_seasons.cum_start_mmdd`가 비어 있으면 적산온도를 내지 않는다(적산 계열은 D1-3) ⑥ `farm_calc_status` 에서 croplib-dp 가 쓰는 열은 `done_at` · `result` · `error` · `calc_version`뿐이다.

### `public.app_health`

웹이 데이터베이스에 연결되는지 확인하는 용도입니다. 계산 결과는 담지 않습니다.

| 열           | 형식          | 비어 있어도 되나 | 뜻                     |
| ------------ | ------------- | ---------------- | ---------------------- |
| `id`         | `int`         | 아니요 (기본키)  | 행 번호. 지금은 `1`.   |
| `note`       | `text`        | 아니요           | 상태 메모. 지금은 `ok` |
| `updated_at` | `timestamptz` | 아니요           | 행을 만든 시각         |

### 운영용 함수: `public.db_size_bytes()`

croplib-dp의 DB 용량 감시(400MB 경고, 450MB 오류 알림)를 위한 RPC 함수입니다 (`supabase/migrations/20261108050000_db_size_bytes.sql`, #77). 전체 데이터베이스 크기와 `public` 및 `krei` 스키마에서 용량이 큰 상위 10개 기본 테이블 크기(`pg_total_relation_size`)를 바이트 단위 JSON 객체로 돌려줍니다. 비회원·회원(`anon, authenticated`)의 실행 권한은 완전히 회수되며, 오직 `service_role`만 실행할 수 있습니다.

- **호출:** `POST /rest/v1/rpc/db_size_bytes`
- **반환 규격:**
  ```json
  {
    "db_bytes": 59768832,
    "tables": {
      "heat_daily": 25165824,
      "sun_daily": 15728640,
      "weather_daily": 8388608
    }
  }
  ```

## 바꿀 때의 순서

열을 더하거나 바꾸려면 이 저장소에서 마이그레이션과 이 계약서를 같은 PR로 고치고 버전을 올립니다(v1 → v1.1). 그다음 croplib-dp의 업로드 코드와 계약 검사를 새 버전에 맞추고, 두 PR에 서로의 링크를 답니다. 화면이 아직 쓰는 열은 지우지 않고, 새 열을 더하는 방식으로 바꿉니다.
