# 작업 흐름 — 검토 채팅 쪽 규칙

이 저장소의 일은 **작업창**(Antigravity)과 **검토 채팅**(Claude)이 GitHub 이슈 댓글로 주고받으며 한다.

- **작업창의 단계**(계획 → 승인 대기 → 구현 → PR → 완료 보고 → 검토 대기 → 다음 이슈)는 `CLAUDE.md` "이슈 작업 흐름"에 있다. 작업창은 그 파일을 자동으로 읽는다. 여기에 다시 적지 않는다.
- **이 문서는 검토 채팅 쪽 규칙**이다. 작업창은 이 파일을 읽지 않아도 된다.
- 넘길 때의 "지금 상태"(진행 중 이슈 · 다음 이슈 · 부탁해 둔 확인)는 Claude 프로젝트의 인계서(`claude/CropMon_검토채팅_인계서_*.md`)에 둔다. 규칙은 이 문서, 상태는 인계서.
- 결정 배경: `docs/decisions/0045-issue-driven-workflow.md`.

## 1. 검토 채팅이 맡는 일

- 작업 지시 이슈를 쓴다(라벨 `작업지시`, 해당하면 `회원제 1/1`). 순서표 **#144**를 따라 **하나씩** — 앞 이슈가 병합되면 다음 이슈를 올리고 #144에 번호를 적는다. 병합되면 #144에 체크하고 "→ PR #n 병합 (결정 00xx)"을 붙인다.
- 작업창이 단 `[작업창] 계획`을 읽고 `[검토 채팅] 승인` 또는 `[검토 채팅] 수정`을 단다.
- PR 검토: 바뀐 파일, 지우거나 바꾼 시험(기준을 낮춘 곳이 없는지), SQL, CI. `quality` 통과 뒤 squash 병합하고 `[검토 채팅] 병합함`. DB를 바꾸는 SQL이 있는 PR은 사용자가 SQL을 실행한 뒤 병합한다.
- 한 저장소는 한 검토 채팅만 맡는다. 설계 · 시안이 바뀌어야 하면 사용자에게 알리고, 사용자가 설계 채팅에 가져간다.

## 2. 이슈 쓰는 법

- **작업창은 Claude 프로젝트 문서를 못 본다.** 이슈 본문에 왜 · 기준(수치 · 문구) · 범위 · 범위 밖 · 주의 · 완료 조건을 스스로 완결되게 옮겨 적는다.
- 쓰기 전에 **지금 코드를 한 번 훑는다**(관련 파일 위치, 이미 있는 함수 · 토큰). 코드와 어긋난 전제를 쓰면 작업창이 계획에서 되묻게 된다.
- 재료는 Claude 프로젝트의 이슈 목록 초안 · 셸 · 회원 설계 문서 · 시안 검토 문서(3절 구현 주의, 4절 결정) · 디자인 규칙.
- 작업창이 PR을 둘로 나누자고 하면: 앞쪽은 `Closes #이슈`, 뒤쪽은 병합 뒤 검토 채팅이 새 이슈로 올린다(#155 → #157).
- 실제 휴대폰에서만 볼 수 있는 것은 PR 본문에 "사용자가 휴대폰에서 확인할 목록"으로 적게 하고, 병합 뒤 사용자에게 그대로 전한다.

## 3. 도구 (Claude Code 세션)

- 저장소 붙이기: `add_repo`(owner `krpeace`, repo `CropMon`, access `push`) → `git clone --depth 1 https://github.com/krpeace/cropmon /home/claude/cropmon` → `register_repo_root`. 처음에 권한 검사에서 거절되면 사용자에게 승인 창 허용을 부탁하고 다시 시도한다.
- `gh`는 REST만 된다(GraphQL 막힘).
  - 댓글: `gh api repos/krpeace/cropmon/issues/<n>/comments` (쓰기는 `-F body=@파일`)
  - 새 이슈: `gh api repos/krpeace/cropmon/issues -f title=… -F body=@파일 -f "labels[]=작업지시"`
  - 이슈 본문 고치기: `gh api -X PATCH repos/krpeace/cropmon/issues/<n> -F body=@파일`
  - 열린 PR: `…/pulls?state=open`, 바뀐 파일: `…/pulls/<n>/files?per_page=100`
  - 병합: `gh api -X PUT …/pulls/<n>/merge -f merge_method=squash`, 가지 갱신: `gh api -X PUT …/pulls/<n>/update-branch`
  - CI: `…/commits/<sha>/check-runs`, 실패 로그: `…/actions/jobs/<id>/logs`
  - 가지 지우기(`git/refs` DELETE)는 막혀 있다.
  - PR 코드 보기: `git fetch --depth 3 origin pull/<n>/head` 뒤 `git diff <base> FETCH_HEAD`.
- 문서만 바꾼 PR도 `format:check`에 걸릴 수 있다: `npx -y prettier@3.9.10 --no-config --write <파일>`.
- 커밋 · PR 끝에는 세션이 주는 표시 줄을 붙인다.

## 4. 예약 확인

- 사용자는 개입을 최소로 하길 원한다. 작업이 도는 동안 **약 30~45분 간격으로 `send_later`를 이어 건다**(작업창 기다림 120분보다 짧게). 예약 메시지에는 다음에 무엇을 보고, 무엇을 기준으로, 무엇을 할지 구체적으로 적는다.
- 계획이나 PR이 아직 없으면 30분 뒤 다시 본다. 두 번 연속 없으면 사용자에게 작업창 상태를 봐 달라고 한다. 작업창이 멈췄으면 작업창에 "CLAUDE.md 이슈 작업 흐름대로 다음 작업지시 이슈를 찾아 시작해"(또는 "PR #n 수정 요청 읽고 고쳐 줘")를 넣어 달라고 한다.
- 사용자에게는 병합 · 막힘 · 휴대폰 확인 요청 · 사용자 결정이 필요할 때만 짧게 알린다.

## 5. 새 채팅으로 넘기기

검토 채팅은 예약 확인 때마다 대화 전체를 다시 읽으므로, 대화가 길어지면 확인 한 번이 느리고 비싸진다. 채팅은 남은 용량을 정확히 볼 수 없으므로 셀 수 있는 기준으로 판단한다.

- **기준** — 하나라도 닿으면 검토 채팅이 **먼저** 넘기기를 권한다.
  - 이 채팅에서 병합한 PR이 **5개**가 됨
  - 예약 확인이 **8번** 돌아옴
  - 이 채팅을 연 지 **12시간**이 지남
  - 순서표 #144의 **이정표(M0~M4)가 끝남** — 이때는 늘 넘긴다
  - 앞에서 읽은 문서 · 코드를 다시 찾게 됨
- **넘기는 때**: 검토 채팅이 하다 만 검토가 없을 때. 작업창이 계획 승인이나 PR 검토를 기다리는 중이어도 된다(새 채팅이 이어서 댓글을 달면 작업창이 그대로 읽는다).
- **넘기는 순서**
  1. 인계서의 "지금 상태"를 고친다: 열린 이슈 · PR, 작업창이 무엇을 기다리는지, 다음 이슈, 사용자에게 부탁해 둔 확인, 알려진 남은 것.
  2. 이 채팅에 걸린 예약을 **지운다**(남겨 두면 옛 채팅으로 돌아온다).
  3. 사용자에게 새 채팅 첫 메시지를 드린다: "claude/CropMon_검토채팅_인계서_<날짜>.md 읽고 CropMon 검토 채팅을 이어받아줘."
- 새 채팅은 저장소를 붙이고 이 문서와 인계서를 읽은 뒤, 인계서의 "처음 할 일"부터 한다.
